# Spec: Web version of an uploaded video

Status: implemented on the `transcode-web-video` branch; this document is the
retroactive executable spec that redevelopment follows.

This document is an **executable spec** (spec-driven development): it is the
prompt an implementing session works from and the authoritative record of every
decision, not a background sketch. Resolve ambiguity by reading this doc, not by
inventing; if a genuinely new decision comes up, write it into the doc as part
of the task. Check off tasks (`[x]`, with date) as they land. Do not duplicate
CLAUDE.md conventions here (test-first, pytest style, CSS units, translations in
both locales).

## Motivation

An uploaded video is served for inline playback in the browser, both on the
uploaded-file detail page and in the transcript editor's media player. Two
properties of the original upload get in the way of that:

- **Format.** Uploads arrive in whatever container and codec the source
  produced: MOV/QuickTime, MKV, HEVC, and so on. A browser's `<video>` element
  decodes only a small set of these. When it cannot decode the upload, playback
  fails and the user has to download the file to view it.
- **Size.** Source recordings are full resolution and high bitrate, sometimes
  several gigabytes. Streaming the original to a transcript editor that only
  needs a reference picture wastes bandwidth and delays the first frame.

The feature generates one derived file per video: a 480p H.264/AAC MP4 with
faststart, produced once in a background task after the upload is assembled. The
inline players stream that derived file when it exists and fall back to the
original otherwise. The derived file is decodable by every browser and is far
smaller than the source, so it fixes both problems for the playback surfaces
without altering the stored original, which downloads and transcription continue
to use unchanged.

## Non-goals (v1)

Do not add these, even where they would be easy:

- **No poster image.** Generating a still frame as a poster is a **separate
  feature with its own spec.** It shares the `web/` subdirectory, the
  `task_assemble_chunks` enqueue site, the `media.py` module and the 0013
  migration with this feature, but none of its decisions belong here. This spec
  covers only `has_web_video`, `web_video_path`, `transcode_to_web_video`,
  `task_generate_web_video` and the streaming preference. The `has_poster`
  field, `poster_path`, `extract_poster_image`, `task_generate_poster`, the
  poster view and the "Regenerate poster" control belong to the poster spec.

- **No web version for audio uploads (WAV etc.).** Considered and deferred; see
  "Audio uploads" below for the full reasoning. Only video uploads get a derived
  web file in v1. `task_generate_web_video` returns early for anything that is
  not a video.

- **No conditional or threshold-based transcoding.** Every video upload is
  transcoded, including one that is already a browser-friendly small MP4. The
  alternative is to probe the original's container, codec, resolution and
  bitrate and skip the transcode when it is already a 480p-or-smaller H.264/AAC
  MP4. That check is several ffprobe fields of logic to avoid one re-encode of
  an already-small file, and getting it wrong means serving an undecodable
  original. Transcoding unconditionally is simpler and always produces a file
  the browser can play. The model help text therefore must not claim the
  derived file is produced only "for large videos" (it is produced for every
  video); see the `has_web_video` field below.

- **No multiple renditions or adaptive bitrate.** One 480p rendition, not a
  ladder of resolutions and not HLS/DASH. The playback surfaces are a reference
  player in a transcript tool, not a consumer video site.

- **No on-the-fly / on-request transcoding.** The derived file is produced once
  by a background task and stored on disk. A request never triggers a
  transcode; it either finds the derived file or falls back to the original.

- **No retry, backoff or progress reporting.** A failed transcode leaves
  `has_web_video` false and is logged (see `_log_failure`); the original keeps
  serving. There is no automatic re-enqueue and no user-visible progress. A
  manual re-run is possible by re-enqueuing `task_generate_web_video`, but no UI
  exposes it in v1.

## Audio uploads (decided: deferred, not part of v1)

The open question was whether an uploaded audio file, for example an
uncompressed WAV, should also get a derived "web version". The decision is to
**not** do it in v1, but both halves of the motivation partly apply, so this is
a scoping decision rather than a case where the need is absent:

- **The compatibility half applies to a subset of audio formats, not to WAV.**
  Browsers decode PCM WAV, MP3, AAC/M4A, FLAC, Ogg Vorbis and Opus natively, so
  those already play inline. But some formats an archive receives do **not**
  play in the major browsers and would need a derived version to be playable at
  all: **WMA** (no major browser), **AIFF** (Safari only), **ALAC** (Safari
  only), **AMR** (none) and lossless/exotic codecs such as **APE / Monkey's
  Audio**, **WavPack** and **RealAudio** (none). For an oral-history archive
  these are not hypothetical; old voice recordings arrive as WMA, AIFF and AMR.
  A non-PCM **WAV** (ADPCM, GSM and similar) can also fail to decode even though
  the `.wav` container is otherwise fine.
- **The bandwidth half applies to uncompressed sources.** A raw stereo WAV at
  44.1 kHz/16-bit is about 600 MB per hour; a compressed web version (AAC or
  Opus, roughly 128 kbps) would cut that by about an order of magnitude. That is
  a real saving, but only for uncompressed or lightly compressed sources. An
  upload that is already MP3/AAC/Opus gains nothing.
- **A different shape than the video feature.** Video is transcoded
  unconditionally, because the derived file always earns its keep through
  downscaling even when the source already plays. Audio would more likely be
  **conditional**: derive a web version only when the source format is one the
  browser cannot play (compatibility) or is uncompressed and large (bandwidth),
  and skip it for an audio upload that already plays and is already small. That
  condition is extra logic the video path does not have.
- **The mechanism does not carry over.** `transcode_to_web_video` is
  video-specific: the scale filter, `libx264`, `yuv420p` and the MP4/faststart
  container are all about video. An audio web version needs its own transcode
  function (source → AAC in `.m4a`, or Opus), its own `has_web_audio` flag, its
  own `web_audio_path`, its own conditional task branch and its own served
  content type. It is a parallel feature, not a flag on this one.

The layout in this spec is chosen so that a later "web audio" feature drops in
without rework: derived files live under a `web/` subdirectory keyed on the full
filename, `stream_source()` is the single place that decides which file to serve
and can prefer a compressed audio version the same way it prefers the web video,
and the enqueue site in `task_assemble_chunks` already fans out per media type.
When that feature is specified, it gets its own dated spec, and it decides the
condition under which an audio upload is transcoded.

If this decision should change, flip it here first, then implement.

## Feature reference

### Model field

Added to [`UploadedFile`](../app/mmt/uploaded_files/models.py):

```python
has_web_video = models.BooleanField(
    default=False,
    verbose_name=_('Has web video'),
    help_text=_(
        'A 480p web-friendly version is generated automatically with a '
        'background job for videos.'
    ),
)
```

The help text says "for videos", not "for large videos": every video is
transcoded (see the conditional-transcoding non-goal). The field is set to
`True` only by `task_generate_web_video` after a successful transcode, and it is
the gate `stream_source()` checks before preferring the derived file.

The migration
[`0013_uploadedfile_has_web_video`](../app/mmt/uploaded_files/migrations/0013_uploadedfile_has_web_video.py)
adds this field, and only this field. The original implementation added
`has_web_video` and `has_poster` together in a single migration named
`0013_uploadedfile_has_poster_uploadedfile_has_web_video`; the redevelopment
implements the two features in separate slices, so each field arrives in its own
migration and the poster field gets the next free number when the poster spec is
implemented.

### Derived-file path

```python
@property
def web_video_path(self) -> Path:
    return self.file_path.parent / 'web' / (self.filename + '.mp4')
```

- **`web/` subdirectory** beside the original, not beside the chunks. Keeping
  derived files in their own directory keeps the upload directory listing equal
  to the set of original files.
- **`self.filename + '.mp4'`**, i.e. the full stored filename with `.mp4`
  appended, not the stem with the suffix replaced. `filename` is unique per
  project (`unique_filename` constraint), so appending inherits that uniqueness
  and two uploads that differ only in extension (`clip.mov`, `clip.mp4`) never
  collide on their derived file. This mirrors how
  [`FileChunk.chunk_path`](../app/mmt/uploaded_files/models.py) appends to the
  full name.

### Serving preference

`stream_source()` is the single decision point for which file the inline player
receives:

```python
def stream_source(self) -> tuple[Path, str]:
    if self.has_web_video and self.web_video_path.is_file():
        return self.web_video_path, 'video/mp4'
    return self.file_path, self.media_type
```

- Prefers the derived file **only when both** the flag is set **and** the file
  is present on disk. The `is_file()` check is not redundant with the flag: if
  the derived file is deleted from disk after the flag was set, the method must
  fall back to the original rather than serve a path that will 404. The test
  `test_stream_falls_back_to_original_when_web_video_file_missing` pins this.
- The fallback serves the **original** upload with its detected `media_type`,
  which is what the browser gets while the transcode is still running, when the
  transcode failed, or when the source was already browser-friendly and the
  transcode has not finished yet.
- The [`stream`](../app/mmt/uploaded_files/views.py) view calls
  `stream_source()`, checks `is_file()` on the returned path, and passes both
  the path and content type to
  [`serve_file`](../app/mmt/core/file_serving.py). Nothing else in the view
  changes; range requests, headers and permissions are handled by `serve_file`
  exactly as before.

The [`download`](../app/mmt/uploaded_files/views.py) view is deliberately **not**
changed: a download always serves the original upload, never the 480p derived
file.

### Transcode helper

[`transcode_to_web_video(src, dst) -> bool`](../app/mmt/uploaded_files/media.py)
in the `media.py` module (the module renamed from `analysis.py`; it holds every
ffmpeg/ffprobe helper). The exact ffmpeg invocation is decided, not left to the
implementer, because each flag has a reason:

```python
cmd = [
    'ffmpeg',
    '-y',
    '-i', str(src),
    '-map', '0:v:0',
    '-map', '0:a:0?',
    '-vf', "scale=-2:'min(480,floor(ih/2)*2)'",
    '-c:v', 'libx264',
    '-profile:v', 'high',
    '-preset', 'medium',
    '-crf', '23',
    '-maxrate', '1500k',
    '-bufsize', '3000k',
    '-force_key_frames', 'expr:gte(t,n_forced*1)',
    '-pix_fmt', 'yuv420p',
    '-movflags', '+faststart',
    '-c:a', 'aac',
    '-b:a', '160k',
    '-ac', '2',
    str(tmp),
]
```

Decided conventions:

- **Explicit stream mapping (`-map 0:v:0`, `-map 0:a:0?`).** Only the first
  video stream and, if present, the first audio stream. The `?` makes the audio
  mapping optional so a video without an audio track still transcodes
  (`test_transcode_to_web_video_handles_source_without_audio`). ffmpeg's default
  auto-selection would pull in subtitle or data streams depending on the ffmpeg
  version; the explicit mapping drops them
  (`test_transcode_to_web_video_drops_subtitle_streams`).
- **Scale filter `scale=-2:'min(480,floor(ih/2)*2)'`.** Height is capped at 480
  and never upscaled (`min` with the source height); width is derived from the
  aspect ratio. `yuv420p` requires **even** dimensions. `-2` fixes the width to
  an even number but not the height, so `floor(ih/2)*2` rounds the source height
  down to even before the `min`. Without it an odd-height source below 480p
  (for example 361px) would fail
  (`test_transcode_to_web_video_handles_odd_height_source`), and a source above
  480p is unaffected because 480 is already even.
- **H.264 high profile, `-preset medium`, `-crf 23`, capped at `-maxrate 1500k`
  / `-bufsize 3000k`.** CRF 23 is the quality target; the maxrate/bufsize pair
  caps the bitrate so a high-motion source cannot produce an oversized file.
- **`-pix_fmt yuv420p`** keeps the output decodable by every browser (some
  decoders reject 4:2:2 / 4:4:4).
- **`-movflags +faststart`** moves the MP4 index to the front so playback can
  begin before the whole file has downloaded.
- **Audio AAC, `-b:a 160k`, `-ac 2`.** Stereo AAC at 160 kbps.
- **Atomic write.** The command writes to a temporary sibling
  `dst.parent / (dst.stem + '.tmp' + dst.suffix)` and `tmp.replace(dst)` only on
  success. A failed or interrupted encode leaves no half-written `dst`
  (`test_transcode_to_web_video_timeout_returns_false_and_leaves_no_output`,
  `test_transcode_to_web_video_failure_returns_false_and_leaves_no_output`). The
  destination directory is created with `mkdir(parents=True, exist_ok=True)`
  first (`test_transcode_to_web_video_creates_missing_destination_dir`).
- **Timeout `TRANSCODE_TIMEOUT = 4 * 60 * 60`.** A ceiling so a hung ffmpeg
  cannot occupy a worker forever; generous enough for a multi-hour recording on
  a slow machine. A timeout returns `False` and removes the temp file.
- **Return value.** `True` on success, `False` on
  `subprocess.CalledProcessError` or `subprocess.TimeoutExpired`. On failure the
  helper calls `_log_failure('Web video transcode', src, exc)`, which logs a
  warning with the tail of ffmpeg's stderr
  (`test_transcode_to_web_video_logs_stderr_on_failure`).

### Background task

[`task_generate_web_video(uploaded_file_id)`](../app/mmt/uploaded_files/tasks.py):

```python
@shared_task
def task_generate_web_video(uploaded_file_id: int) -> None:
    uploaded_file = UploadedFile.objects.get(pk=uploaded_file_id)
    if not uploaded_file.is_video():
        return
    if transcode_to_web_video(uploaded_file.file_path, uploaded_file.web_video_path):
        UploadedFile.objects.filter(pk=uploaded_file_id).update(has_web_video=True)
```

- **Returns early for non-video files** (`is_video()` is false for audio and
  everything else), so an audio upload never reaches the video transcode
  (`test_task_generate_web_video_skips_non_video`).
- **Sets `has_web_video=True` only on a successful transcode.** A failed
  transcode leaves the flag false and the original keeps serving
  (`test_task_generate_web_video_leaves_flag_unset_when_transcode_fails`).
- **Writes with a filtered `.update()`**, not `save()`, so it touches only the
  one column and cannot clobber a concurrent write to the row.

### Enqueue and synchronous media-type detection

[`task_assemble_chunks`](../app/mmt/uploaded_files/tasks.py) detects the media
type **synchronously**, in the assembly task itself, and only then enqueues the
follow-up tasks:

```python
@shared_task
def task_assemble_chunks(uploaded_file_id: int) -> None:
    uploaded_file = UploadedFile.objects.get(pk=uploaded_file_id)
    try:
        uploaded_file.assemble_chunks()
    except Exception:
        # Reset the flag so the file drops back to 'incomplete' and the final
        # chunk can be re-sent to retry assembly.
        UploadedFile.objects.filter(pk=uploaded_file_id).update(assembling=False)
        raise
    # The media type is detected here rather than in a task of its own because
    # the decision whether to enqueue the poster and the web video depends on
    # it. A separate task would run concurrently with them, so the media type
    # would still be undetected at the moment those tasks are enqueued and a
    # video would be treated as a non-video. detect_media_type reads the file
    # header in-process with libmagic, which takes milliseconds and does not
    # need a worker of its own.
    media_type = detect_media_type(uploaded_file.file_path)
    if media_type:
        uploaded_file.media_type = media_type
        UploadedFile.objects.filter(pk=uploaded_file_id).update(media_type=media_type)
    calculate_duration.delay(uploaded_file_id)
    calculate_server_checksum.delay(uploaded_file_id)
    if uploaded_file.is_video():
        task_generate_web_video.delay(uploaded_file_id)
```

Decided conventions:

- **The `task_update_media_type` task is removed.** It had exactly one caller,
  `task_assemble_chunks`, and its body moves inline. Its behavior is unchanged
  otherwise: a `None` result from `detect_media_type` leaves the existing
  `media_type` alone, and the write is a filtered `.update()` on the single
  column. The in-memory assignment before the write is what makes `is_video()`
  on the same instance see the detected type.
- **Non-video uploads never enqueue a transcode.** An audio upload or any other
  file costs no queued message, no worker slot and no database fetch for a task
  that would return immediately
  (`test_task_assemble_chunks_does_not_enqueue_web_video_for_audio`).
- **The `if uploaded_file.is_video():` branch is the extension point for other
  video-only follow-ups.** `task_generate_poster` is not part of this spec and
  does not appear here; the poster feature adds its own `delay()` call inside
  this branch, before the web video, and that line belongs to the poster spec.
  Whichever of the two features is implemented first creates the branch.
- **`task_generate_web_video` keeps its own `is_video()` guard.** The check at
  the enqueue site does not replace the check in the task. The task is enqueued
  from one place today but is also re-runnable by hand, so the guard stays at
  the boundary that does the work.
- **The web-video task is still enqueued last**, after the poster, so on a
  single FIFO worker the cheap tasks finish before the slow transcode. With
  parallel workers the order does not matter, since none of these tasks depend
  on each other
  (`test_task_assemble_chunks_assembles_and_enqueues_followups`).

Note: the assembled-upload path (`task_assemble_chunks`) enqueues the transcode.
The single-request `upload` view path enqueues only duration and checksum today
and does not enqueue the transcode; that asymmetry is pre-existing and out of
scope for this spec.

### Admin

[`UploadedFileAdmin`](../app/mmt/uploaded_files/admin.py) lists `has_web_video`
in `readonly_fields` so an operator can see on the change page whether the
derived file was produced, without being able to edit the flag by hand. The
field is deliberately **not** added to `list_display`: the changelist is already
wide, and whether a single file has a derived web version is only interesting
when looking at that file.

### Frontend

No web-video-specific frontend change is required. The detail-page `<video>`
and the transcript editor's media player already point at the
`uploaded_files:stream` URL, and `stream_source()` decides server-side which
file that URL yields. The players do not know whether they received the derived
file or the original. (The `poster` attribute and the `hasPoster` dataset
plumbing in the media components belong to the poster feature, not this one.)

## Tests

The transcode tests build a real tiny clip with ffmpeg (`make_video`) and probe
the output with ffprobe (`probe_video`, `probe_stream_types`); they exercise the
real encoder, not a mock, except where the failure path is forced.

### `tests/test_media.py` — `transcode_to_web_video`

- **`test_transcode_to_web_video_downscales_to_480p_h264`** — a 720p source
  yields an `h264` stream at height 480.
- **`test_transcode_to_web_video_does_not_upscale`** — a 360p source stays at
  height 360.
- **`test_transcode_to_web_video_handles_odd_height_source`** — a 361px source
  (encoded lossless `yuv444p` so odd dimensions are representable) transcodes to
  even height 360 rather than failing.
- **`test_transcode_to_web_video_drops_subtitle_streams`** — a source with a
  subtitle stream yields exactly `['video', 'audio']`.
- **`test_transcode_to_web_video_handles_source_without_audio`** — a
  video-only source yields exactly `['video']`.
- **`test_transcode_to_web_video_creates_missing_destination_dir`** — the `web/`
  parent is created when absent.
- **`test_transcode_to_web_video_failure_returns_false_and_leaves_no_output`** —
  a non-video input returns `False` and writes no `dst`.
- **`test_transcode_to_web_video_timeout_returns_false_and_leaves_no_output`** —
  a mocked `TimeoutExpired` returns `False`, asserts a positive `timeout` kwarg
  was passed, and leaves the directory empty (no temp file).
- **`test_transcode_to_web_video_logs_stderr_on_failure`** — a non-video input
  logs a warning containing the source path and ffmpeg's stderr complaint.

### `tests/test_tasks.py` — `task_generate_web_video` and enqueue

- **`test_task_generate_web_video_transcodes_and_sets_flag`** — with
  `transcode_to_web_video` mocked to return `True`, the task calls it with
  `(file_path, web_video_path)` and sets `has_web_video=True`.
- **`test_task_generate_web_video_leaves_flag_unset_when_transcode_fails`** —
  with the transcode mocked to return `False`, `has_web_video` stays `False`.
- **`test_task_generate_web_video_skips_non_video`** — for an audio upload the
  transcode is never called and `has_web_video` stays `False`.
- **`test_task_assemble_chunks_assembles_and_enqueues_followups`** — after
  assembly of a video, `task_generate_web_video.delay` is called once with the
  file pk (alongside the other follow-up tasks), and the `media_type` column
  holds the detected type when the task returns.
- **`test_task_assemble_chunks_does_not_enqueue_web_video_for_audio`** — for an
  audio upload, `task_generate_web_video.delay` is not called, while the
  duration and checksum tasks still are. This is the test that pins the
  synchronous detection: with the detection in a separate task the media type
  would still be undetected at the enqueue point and the assertion would not
  hold.

### `tests/test_views.py` — stream preference

- **`test_stream_prefers_web_video_when_available`** — with the flag set and the
  derived file on disk, the response is `Content-Type: video/mp4` and its body
  is the derived file's bytes.
- **`test_stream_serves_original_when_no_web_video`** — with no derived file the
  response is the original with its `media_type` (`video/quicktime`).
- **`test_stream_falls_back_to_original_when_web_video_file_missing`** — with the
  flag set but the derived file deleted from disk, the response is the original,
  not a 404.

## Assumptions

- `ffmpeg` and `ffprobe` are on `PATH` in the worker image, as the existing
  waveform and duration helpers already require.
- The transcode runs in a Celery worker, not in the request cycle; the request
  cycle only reads `has_web_video` and the derived file.
- `is_video()` (via `file_category(media_type)`) is reliable at the enqueue
  point and inside `task_generate_web_video`, because `task_assemble_chunks`
  detects the media type synchronously before enqueuing anything. The only case
  left is a file whose type `detect_media_type` cannot determine at all; it is
  not transcoded, and the original keeps serving.
